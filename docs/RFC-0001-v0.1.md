# RFC-0001: ai-lb v0.1 Architecture

- Status: **proposed** (nothing here is implemented).
- Scope: desktop GUI application for pooled AI coding accounts
  (Codex, Antigravity) with a local OpenAI-compatible API gateway.
- Companion: [ARCHITECTURE.md](../ARCHITECTURE.md) (high-level overview).

All endpoint names, field names, ports, and behaviors below are **design
proposals**, not shipped behavior.

## 1. Context

Users hold several AI coding accounts (subscriptions, promo accounts, team
seats) across providers such as Codex and Antigravity. Today they either
manually re-login to switch accounts or run ad-hoc proxies per provider.
ai-lb aims to be one local place that: keeps the account pool with plan and
quota visibility; switches the official client between accounts safely; and
serves the pool through one OpenAI-compatible local API with its own
key-based access control.

Two existing projects inform the design (inspiration only, no code taken):

- `jlcodes99/cockpit-tools` — local-first multi-account management, per-IDE
  account lifecycle, quota polling and display, Tauri desktop shape.
- `Soju06/codex-lb` — account pooling with an API-key proxy, routing with
  retry/failover, per-account usage accounting, OpenAI-compatible surface.
- `openai/codex` (official client) — protocol and auth reference for the
  Codex side; ai-lb must interoperate with it, not reimplement it.

## 2. Goals (v0.1)

- G1. Manage multiple Codex and multiple Antigravity accounts in one GUI:
  identity, plan/subscription, quota windows, reset times, health.
- G2. Switch the official Codex / Antigravity client to a chosen account as
  a safe, verifiable, rollback-capable transaction.
- G3. Serve a loopback-only OpenAI-compatible API (`/v1`) routed over
  user-selected account pools, with API-key auth, deterministic
  quota-aware routing, retry/failover, streaming, and usage accounting.
- G4. Manage API access as first-class entities: clients, rotatable keys,
  access policies (expiry, rate, concurrency, budgets, model/pool/IP
  restrictions), and usage records.
- G5. Keep all secrets in OS credential storage and all metadata in a local
  SQLite file; store no prompt/response bodies by default.
- G6. Ship as one signed desktop app for macOS, Windows, and Linux with
  tray/background operation.

## 3. Non-goals (v0.1)

Cloud control plane; hosted SaaS; Kubernetes; multi-node clusters;
PostgreSQL server; Redis; distributed routing; billing platform; payment
processing; teams/organizations; own remote-relay infrastructure; mobile
apps; LAN/remote exposure of the gateway; ML-based routing; prompt/response
body retention.

## 4. Product flows

### 4.1 Add account

```text
Add (OAuth device flow / token import / read current client login)
  → validate against provider → store metadata in SQLite,
    secrets in SecretStore → initial quota/subscription fetch
  → account appears with status, plan, quota windows
```

Import of the *currently logged-in* client account (same idea as the
local-first reference) is required UX: the user should not have to
re-authenticate just because ai-lb exists.

### 4.2 Observe and refresh

Accounts screen shows per account: provider, identity, plan, subscription
status/expiry (only if the provider exposes it), quota windows with reset
times, CLI-active marker, Local API pool membership, health. Refresh is
manual (button) plus a background poller with a configurable interval.
Failed polls mark snapshots `stale`, never zero them silently.

### 4.3 Switch CLI account (summary)

```text
quota exhausted → user picks another account → Switch
  → validate → backup client state → stop/reload → activate
  → restart/reload → verify new active account → done (rollback on failure)
```

Full transaction in §11.

### 4.4 Use the Local API

```text
operator creates ApiClient + key (secret shown once)
  → selects pool accounts, policies
  → client calls http://127.0.0.1:<port>/v1 with the key
  → gateway authenticates, checks policies, routes, accounts usage
```

### 4.5 Rotate a key

Client holds two keys (current + retiring): create successor → distribute
→ verify traffic on successor → revoke predecessor. Revocation is
immediate; in-flight requests drain, new ones are rejected.

## 5. Tech stack comparison

Candidates: (A) Tauri 2 + Rust core + TypeScript web frontend;
(B) Electron + TypeScript; (C) Wails v2 + Go backend + web frontend.

| Criterion | A: Tauri + Rust | B: Electron + TS | C: Wails + Go |
|---|---|---|---|
| Filesystem integration | Excellent (Rust std + plugins) | Excellent (Node) | Excellent (Go stdlib) |
| OS credential storage | Good (`keyring` crate + platform APIs) | Good (electron `safeStorage`, OS-specific limits) | Fair (Go keyring libs thinner, more glue code) |
| Process management | Excellent (tokio processes, sidecar support if ever needed) | Good (child_process; heavier runtime) | Excellent (os/exec, goroutines) |
| Local HTTP server | Excellent (axum/hyper in-process, no extra runtime) | Good (Node http; fine but shares event loop with UI backend) | Excellent (net/http) |
| Tray / background | First-class (autostart, tray, window-hide) | Good, heavier | Good |
| Win/macOS/Linux parity | Good (WebView2/WKWebView/WebKit; test matrix needed) | Best (bundled Chromium) | Good (system webview, same caveat as Tauri) |
| Memory footprint | Typically lower runtime overhead than Electron (system webview, no bundled Chromium) | Large (Chromium per window) | Small |
| Packaging / updates | Good (bundler + updater) | Best tooling, biggest artifacts | Good, younger ecosystem |
| Maintainability | One core language (Rust) + TS UI; Rust learning curve is the cost | Single language (TS) everywhere; lowest hiring/learning barrier | Go backend is easy to hire for; desktop ecosystem smallest |
| Provider adapters | Strong typing, good TLS/HTTP/OAuth crates; reverse-engineered flows need care in any language | Same flows in TS; largest library surface for OAuth/HTTP quirks | Good HTTP story; fewer reference implementations to compare against |
| Security surface | Small runtime, Rust memory safety, least code with secret access | Chromium + Node widen the surface; `safeStorage` differs per OS | Small runtime, memory-safe GC language |

Reference note: the closest local-first reference (`cockpit-tools`) is a
Tauri app, which gives the Tauri+Rust path directly comparable prior art
for the desktop shape. The closest pooling proxy (`codex-lb`, Python/FastAPI)
is a reference for pooling, routing, retry/failover, OpenAI-compatible
proxying, and usage accounting only — not a language argument for or
against Rust.

## 6. Selected stack

**Decision: A — Tauri 2 + Rust core + TypeScript web frontend (Vite-based;
exact UI framework chosen at Phase 1, default React).**

Rationale:

- The hardest parts of ai-lb are backend-shaped (gateway HTTP server,
  routing, quota polling, process supervision, secret storage), and Rust
  owns all of them in one memory-safe core with no second runtime.
- Footprint and trust matter for an always-on local proxy holding OAuth
  tokens; Tauri's small binary and narrow API surface beat Electron here.
- Tray, autostart, safe window-hide, and OS packaging are solved Tauri
  features, not custom code.
- The main cost — Rust proficiency and slower initial velocity versus
  TypeScript-everywhere — is accepted because provider adapters and the
  gateway are long-lived, security-sensitive code where Rust's type system
  and ecosystem (tokio, axum, sqlx, keyring) pay back.
- Wails+Go was the serious alternative (superb HTTP/process story), but its
  desktop ecosystem is the least mature of the three and offers no
  compensating advantage for this workload.

What is deliberately left open: the exact TS UI framework (React default),
the SQLite driver (sqlx vs rusqlite — Phase 1 spike), and the update
channel. None of these change the architecture above.

## 7. Runtime / process architecture

**Decision: one desktop process for v0.1.** No sidecar, no daemon, no
service.

In-process modules and their interaction:

```text
GUI (webview) ⇄ Core (state owner, command dispatcher)
Core ┬ ProviderAdapters (per-request and per-poll use)
     ├ CredentialSessions (bounded in-memory leases over SecretStore, §10.1)
     ├ SQLite (single writer; WAL mode; migrations at startup)
     ├ ProcessManager (spawn/kill/supervise official clients)
     ├ QuotaRefresher (tokio background tasks, per-account schedule + jitter)
     └ Gateway (axum server on 127.0.0.1:<port>, same tokio runtime)
```

GUI-closed behavior: closing the window hides to tray; the process keeps
running so the gateway and refresher continue. Explicit Quit stops the
gateway (drain in-flight, then bind-close), stops the refresher, and exits.
A headless/background mode (no window at login) is future work — the
process model already permits it because no module depends on a visible
window.

Why not a sidecar (the local-first reference embeds a proxy sidecar):
a sidecar buys independent restart and language freedom, but costs an IPC
protocol, two release artifacts, secret hand-off between processes, and a
harder single-file story. None of that is justified before v0.1 proves the
core. Revisit only if crash isolation or a headless daemon demands it.

## 8. Provider interface

### 8.1 Contract shape

```text
ProviderAdapter            # one instance per provider (Codex, Antigravity)
├── identity              # provider id, display name, adapter version
├── capabilities          # ProviderCapabilities flags (explicit, §8.2)
├── accounts              # listAccounts, importCurrentAccount, loginAccount,
│                         #   removeAccount (metadata + secrets), validateAccount
├── subscription+quota    # refreshAccount, getAccountInfo,
│                         #   getSubscriptionInfo, getQuota
├── activation (CLI)      # getActiveAccount, activateAccount,
│                         #   backupClientState / restoreClientState
└── client process        # detectInstallation, isClientRunning,
                          #   stopClient, startClient, restartClient
```

Exact method names are illustrative; the normative split is: **account
lifecycle + metadata + activation + process control belong in the shared
contract; everything upstream-shaped stays provider-specific** behind it
(credential file layouts, OAuth/token flows, quota JSON shapes, process
names/args, IPC or reload hooks).

### 8.2 Capabilities

```text
ProviderCapabilities
├── cliSwitching        # can activate accounts into the official client
├── quota               # exposes machine-readable quota
├── quotaWindows        # quota decomposes into labeled windows w/ resets
├── subscriptionInfo    # plan/status/expiry actually available
├── localApi            # accounts usable as gateway pool members
├── tokenRefresh        # adapter can refresh tokens itself
└── safeRetry           # provider offers an idempotency mechanism
                        # ai-lb may use (else §13 conservative rules apply)
```

A capability absent means "not supported", surfaced in the GUI as such —
never a silent no-op. v0.1 requires `cliSwitching` + `localApi` for Codex
and Antigravity; `quota`/`subscriptionInfo` are adopted per provider as
available.

### 8.3 Adapters

- `CodexAdapter` — official Codex client interop (detect install, read and
  activate credentials, process control, quota/subscription mapping).
- `AntigravityAdapter` — same contract, Antigravity-specific storage and
  client control.

No credential-layout or endpoint assumptions are frozen here: exact file
paths, config formats, and quota mappings are discovered by implementation
spikes against the real clients and recorded then. The architecture only
guarantees they stay inside the adapter.

### 8.4 Errors

Adapters return typed errors the core can act on without parsing strings:

```text
AdapterError
├── auth (invalid / expired / revoked)
├── rateLimited (with retry hint if supplied)
├── quotaExhausted (with reset hint if supplied)
├── network / upstream5xx
├── clientNotInstalled / clientLaunchFailed
└── unknown
```

Routing (§13) and health (§18) key off these categories.

## 9. Account / subscription / quota models

Provider-neutral, stored in SQLite (metadata only):

```text
Account
├── id                  # ai-lb uuid
├── provider            # codex | antigravity | (future)
├── identity            # login email / username / external id (as available)
├── plan                # display string as reported, e.g. "Plus"
├── subscription        # SubscriptionInfo (below)
├── status              # ok | refresh_failed | auth_failed | disabled
├── quota               # latest QuotaSnapshot (below)
├── local_api_enabled   # pool membership flag
├── priority / weight   # routing preference (default equal)
└── credentials_ref     # opaque SecretStore key — never the secret itself
```

```text
SubscriptionInfo
├── plan                # string as reported by provider
├── status              # active | expired | unknown (+ provider raw string)
├── started_at?         # only if the provider exposes it
├── expires_at?         # only if the provider exposes it
└── provider_metadata   # raw JSON blob for fields with no neutral shape
```

Rules: show only what the provider returns. No invented auto-renewal,
billing, or expiry. `unknown` is a first-class status.

```text
QuotaSnapshot
├── windows[]           # dynamic, provider-defined
│   ├── id              # stable per provider+window (e.g. "codex:5h")
│   ├── label           # human label as reported or mapped
│   ├── used_percent? / remaining_percent?
│   ├── limit?          # in provider units, if known
│   ├── reset_at?       # next reset, if known
│   └── raw?            # provider blob for unmapped fields
├── updated_at
└── stale               # true when refresh failed or data aged out
```

The core never hardcodes "5h" or "weekly" windows; the adapter maps
upstream-specific quota into this shape and the GUI renders whatever
windows exist. A snapshot is never silently zeroed: on refresh failure the
previous snapshot stays with `stale = true` and the account health
degrades.

## 10. Secret storage

**Decision: OS credential storage behind a `SecretStore` abstraction;
SQLite holds metadata only.**

```text
SecretStore
├── put(ref, material, attributes)   # create/update
├── get(ref)                         # short-lived handle, TTL-cached in memory
└── delete(ref)                      # on account removal; best-effort wipe
```

Backends: macOS Keychain, Windows Credential Manager, Linux Secret
Service (`libsecret`) or compatible keyring. `credentials_ref` is an
opaque string (e.g. `codex:<account-id>:oauth`) resolving through the
store — the account row never contains token material.

If no supported secure credential store is available (notably Linux
without a keyring), v0.1 fails closed: account secret persistence is
unavailable and the GUI shows an error with setup guidance. No custom
encrypted secret file is implemented in v0.1; a user-master-password
encrypted vault is a future possibility, not the selected architecture.

Token material per account is adapter-defined (OAuth access/refresh pair,
API key, session blob) but always opaque bytes to the core. Refresh is an
adapter operation (`tokenRefresh` capability): refresh in memory, write
back through `put`, never log material. On lock-screen/lock-keyring
failures the operation fails closed with `auth` error, not with a retry
storm.

### 10.1 Credential runtime sessions

The gateway never performs an OS keychain lookup per HTTP request.
`SecretStore` is the durable layer; a separate in-memory abstraction
resolves credentials at request time:

```text
CredentialSession (a.k.a. CredentialLease)
├── acquire(account) → cache hit (valid lease) or
│      SecretStore.get(credentials_ref) → short-lived in-memory session
├── bounded cache (per-account cap, global cap, LRU eviction)
├── TTL (short; refresh independent of gateway traffic)
├── invalidate on: account removal, token rotation/refresh,
│      logout / re-auth
├── clear all on app shutdown (best-effort zeroization of owned buffers;
│      absolute memory wiping is not promised on every platform)
└── keyring locked/unavailable on cache miss → fail closed (no request)
```

Rules: secrets never enter SQLite; the lease cache is bounded with TTL;
invalidation above is normative; credential material is never logged.
Best-effort zeroization applies to buffers ai-lb owns; copies inside
TLS/OS libraries are out of scope.

## 11. CLI switching transaction

Switching is a transaction, not a file copy. The design explicitly rejects
building the architecture around "just overwrite auth.json": Codex and
Antigravity differ in credential/state layout, and a half-written switch
leaves the official client broken.

```text
validate target account (adapter.validateAccount: creds present + usable)
  → snapshot current client state (backupClientState → rollback bundle:
     credential files, config files touched, running or not)
  → stop / prepare client (stopClient if running and provider needs it)
  → activate target credentials (adapter.activateAccount)
  → restart / reload client (startClient / restartClient)
  → verify (getActiveAccount == target AND lightweight upstream check)
  → success: drop rollback bundle (after a grace delay)
  → any step fails: restore rollback bundle, restart/reload, re-verify,
     report the failed step; never leave the client half-switched
```

Concurrency: one switch per provider at a time (per-provider mutex);
a switch blocks pool use of the *target* account for the gateway only if
the adapter declares shared credential state — otherwise (§key decision)
CLI and gateway are independent and switching never disturbs in-flight
gateway requests. Progress and the active step are observable in the GUI;
every step is logged without secret material.

## 12. Local API architecture

Gateway: in-process axum server, default bind `127.0.0.1` with an
ephemeral-or-configured port, single base path `/v1`.

```text
TCP 127.0.0.1:<port> → TLS? no (loopback; future transports in §20)
  → auth (ApiKey) → policy pipeline (§14) → router (§13)
  → adapter call with pooled account credentials (independent of CLI state)
  → stream or JSON back → usage accounting (§15)
```

Route direction for v0.1 (names are intent, not promises):

- `GET /v1/models` — synthesized from pool: providers enabled, models
  the adapters report, key's model policy applied.
- `POST /v1/responses` — request/response + streaming (SSE/chunked
  passthrough, no buffering of full bodies beyond what streaming requires).
- `POST /v1/chat/completions` — request/response + streaming, same
  pipeline as Responses.

Compatibility target: v0.1 targets the OpenAI-compatible model listing,
Responses API, and Chat Completions API surfaces required by common coding
clients. Additional routes are added explicitly rather than blindly
proxied: unknown `/v1/*` routes return a controlled `unsupported_route`
response, never a generic pass-through.

Key independence rule (normative): **the gateway resolves pooled account
credentials through the credential session abstraction (§10.1) per
request and never reads or writes the active CLI credential state.**
Per-request CLI file churn is forbidden by design — it races with the
official client and breaks §11 guarantees. Credential resolution here
means the in-memory lease layer, not an OS keychain lookup per request.

## 13. Routing

Deliberately simple deterministic flow for v0.1 — no ML, no learned
weights:

```text
candidate pool = accounts where local_api_enabled
  → filter enabled?
  → filter healthy? (no open cooldown, status ok)
  → filter quota available? (no window at/over limit without reset passed)
  → filter cooldown expired? (per-account cooldown until timestamp)
  → session affinity? (only with a stable session identifier, §13.1;
       pinned account must have survived the filters above)
  → order by (priority desc, available quota desc, least recent use)
  → select head
```

### 13.1 Session affinity

Affinity applies only when the request carries a stable
session/conversation identifier. Acceptable sources:

- an OpenAI `conversation` identifier, where the route defines one;
- a `previous_response_id` chain for the Responses API, where provider
  semantics require continuity;
- an explicit ai-lb extension header / client-provided session id
  (future; the pipeline reserves a slot for it, it is not designed here).

If no session identifier is present, no conversation is invented —
`client + model` (or any similar hash) is NOT a session and must not pin
traffic. Such requests use ordinary routing. Affinity entries have a TTL,
expire on their own, and drop immediately when the pinned account becomes
unhealthy, exhausted, or cooldown-gated. Affinity never pins to an
unhealthy account and never requires storing prompt content.

### 13.2 Retry / failover invariants

POST generation requests are not idempotent by default, so automatic
retry after an ambiguous failure can duplicate work, usage, or side
effects. v0.1 fixes these invariants instead of building a retry engine:

Retry or fail over to another account only when one of these holds:

- the connection failed before the request was sent;
- the provider explicitly rejected the request before execution;
- a quota/auth/rate-limit error is explicitly confirmed;
- the provider offers an idempotency mechanism the adapter exposes via
  the `safeRetry` capability (§8.2) and ai-lb actually uses for the call.

Never retry automatically (same or another account) when:

- the connection dropped after the request body was sent and acceptance
  is unknown;
- streaming already started and then broke;
- any partial response was already delivered to the client.

Streaming rule (normative): **once response/stream data has been exposed
to the client, automatic account failover is forbidden for that request.**
A broken stream surfaces as a truncated-stream error; the client decides
whether to resume or retry — otherwise duplicate generation, duplicate
usage, or a mixed-account stream can result.

- **Failover:** walk the ordered candidate list within the safe cases
  above; each attempt accounted. Exhaustion returns a structured error
  naming the reason per account (quota / cooldown / auth) without
  leaking secrets.
- **Cooldown:** quota/auth/network failures open a per-account cooldown
  (base delay with jitter, exponential backoff capped; success halves it).
  Cooldown is pool-local state, independent of CLI state.
- **Provider errors:** mapped through `AdapterError` (§8.4); provider-wide
  outages degrade to other providers' accounts when the request allows,
  else fail fast with `provider_unavailable`.

## 14. API clients / keys / policies

```text
ApiClient              # a consumer: person, IDE setup, automation
├── id, name, enabled
├── keys[]             # ApiKey (multiple for rotation)
└── default_policy?    # fallback when key has no override

ApiKey
├── id
├── client_id
├── prefix             # short non-secret lookup id (no secret material)
├── verifier           # SHA-256(full high-entropy key) — only this stored
├── created_at / expires_at? / revoked_at?
├── status             # active | expired | revoked
└── policy?            # per-key AccessPolicy override

AccessPolicy
├── expires_at?                 # hard expiry
├── rate                        # requests/minute, requests/hour
├── max_concurrent_requests
├── token_budget                 # daily / monthly × input / output / total
├── monetary_budget?             # estimated vs actual — only if provider gives cost
├── model_allow / model_deny
├── pool_restriction             # provider / pool / account scoping
└── ip_allow / ip_deny           # CIDR lists; never the sole boundary (§16)
```

Key design (normative for v0.1): the key is a high-entropy random secret
(≥ 256 bits) generated by ai-lb, conceptually `sk-ai-lb-<random>`. Stored
per key: a short non-secret lookup prefix (carries no secret material and
does not meaningfully reduce entropy) plus `verifier =
SHA-256(full key)`, compared in constant time. No password-hashing KDF
(Argon2id deliberately not used): dictionary hardening is unnecessary for
machine-generated high-entropy secrets, and a per-request KDF would add
latency and CPU-DoS surface to every API call. The raw secret exists only
at creation (shown once) and in the holder's hands afterward. The key
format is versioned so the format itself can be rotated later.

Authorization order is normative — policy checks run **before** any
upstream routing or request:

```text
HTTP Request → Authenticate API key → enabled / expiration → IP policy
  → rate limit → concurrency limit → usage/token/budget limit
  → model/pool policy → routing → provider/account → upstream
```

Rate limiting is token-bucket per key (plus per-client aggregate);
concurrency is a semaphore per key; budgets are checked pre-request
(estimate) and settled post-request (actual tokens).

## 15. Usage accounting

Provider-neutral record per request; metadata and counters only:

```text
RequestUsage
├── request_id / client_id / key_id
├── provider / account_id / model
├── input_tokens? / cached_input_tokens? / output_tokens?
├── estimated_cost? / actual_cost?   # only when the provider supplies cost;
│                                    # subscription usage is NOT money
├── started_at / duration_ms
└── status / error_category?         # ok | upstream_error | policy_denied | …
```

**No prompt/response bodies stored by default** — a deliberate privacy
decision, not a missing feature. A future opt-in debug capture (redacted,
size-capped, off by default) is the most that may be considered.
`UsageRecord` aggregates `RequestUsage` rows per key/client/day for the
API Access screens and budget enforcement.

## 16. Security boundaries

1. **Loopback bind** — the gateway listens on 127.0.0.1 only; no auth
   scheme compensates for a wider bind in v0.1.
2. **API-key auth** — hashed secrets, constant-time compare, show-once
   issuance, immediate revocation.
3. **Policy pipeline before upstream** — unauthenticated or over-budget
   traffic never touches provider credentials (§14 order).
4. **Secret separation** — token material only in OS stores + short-lived
   memory; SQLite compromise alone yields no usable credentials.
5. **No body retention** — usage rows contain counters, never conversation
   content (§15).
6. **Client-state backup** — switching never destroys the user's prior
   login without a restorable bundle (§11).
7. **IP restrictions as defense in depth** — useful on loopback (per-app
   expectations) but never the sole boundary; a key without auth is
   rejected regardless of source IP.

Out of scope for v0.1 (documented so nobody assumes them): sandboxing of
official clients, full-disk-encryption enforcement, memory-hardening
beyond standard practice, and any server-side component.

## 17. Persistence

Single SQLite file in the OS-appropriate app data directory
(`~/Library/Application Support/ai-lb`, `%APPDATA%/ai-lb`,
`~/.local/share/ai-lb`), WAL mode, single-writer enforced in-process,
schema migrations at startup with version table.

Stored: accounts (+`credentials_ref`), pools/membership, gateway config,
`ApiClient`/`ApiKey` (prefix+verifier)/policies, `RequestUsage`/`UsageRecord`
(with retention cap + prune job), quota snapshots, health/cooldown state,
client-path settings, app settings. Not stored: secrets, prompt/response
bodies, anything requiring a server.

Crash safety: writes that must survive (key issuance/revocation, policy
changes, account removal incl. `SecretStore.delete`) commit before
acknowledgement; quota/health writes are best-effort and re-pollable.
Backup guidance (export metadata minus secrets; secrets re-imported) ships
with the first runnable version, not here.

## 18. Failure / recovery model

| Failure | Detection | Response |
|---|---|---|
| Quota exhausted (account) | Adapter `quotaExhausted` / window check | Exclude from routing until `reset_at`; GUI shows exhausted + reset |
| Auth failure (account) | `auth` error / refresh failure | Mark `auth_failed`, open long cooldown, exclude from pool, prompt re-login; never delete silently |
| Upstream 5xx / network | `AdapterError` categories | Retry/failover only within the §13.2 safe cases; ambiguous or post-send failures fail fast with a structured error; backoff + jitter |
| Keyring locked/unavailable | `SecretStore.get` failure | Fail closed; affected accounts `auth_failed`-adjacent status, retry on next use |
| SQLite unavailable/corrupt | Startup check / write error | Fail fast with guidance; never silently run credential ops without state |
| Client missing/crash at switch | detect/verify steps | Rollback bundle restore, re-verify, report failed step (§11) |
| Gateway port occupied | Bind failure | Suggest configured alternate / auto-pick free port per setting; log clearly |
| Clock skew (expiry/reset math) | Sanity bounds on `reset_at`/`expires_at` | Treat absurd values as unknown, mark stale, keep serving on other signals |

Health per account: `ok | degraded | exhausted | auth_failed | disabled`
with transition log; flapping is damped by cooldown floors.

## 19. Cross-platform concerns

- **Paths:** client installs, credential files, and data dirs differ per
  OS — all behind adapter methods and a path-detection layer with manual
  override in Settings. No hardcoded user paths.
- **Credential stores:** Keychain (macOS) / Credential Manager (Windows) /
  Secret Service (Linux). No supported store (e.g. keyring-less Linux)
  means fail closed per §10: secret persistence unavailable, GUI shows an
  error with setup guidance.
- **Process control:** client process names, signal semantics
  (TerminateProcess vs SIGTERM), and restart behavior differ — adapter
  owned, with per-OS handling and kill-timeout escalation.
- **Webview parity:** Tauri uses system webviews; UI must be tested on
  WebKitGTK (Linux), WebView2 (Windows), WKWebView (macOS).
- **Permissions:** file/keychain prompts on first use; document why each
  is needed. No admin/root required in v0.1.
- **Packaging:** per-OS installers + updater channel; portable builds are
  future work.

## 20. Future Remote Access (deferred)

Reserved, not designed:

```text
ApiExposure
├── Localhost      # v0.1: the only mode
├── LAN            # future: bind + mTLS / token scoping implications
└── RemoteTunnel   # future: relay or tunnel integration
```

Candidate transports later: ai-lb relay, Cloudflare Tunnel, Tailscale, or
a user-provided reverse proxy. No relay server is designed now. When LAN/
remote arrives, it must reuse the §14 pipeline (auth + policies) unchanged
and add transport auth/encryption analysis — remote exposure never weakens
the v0.1 boundaries.

Neutral naming only: `API Access`, `Remote Access`, `Access Management`.
ai-lb provides technical access-control primitives; whether upstream
provider terms permit any particular sharing is the operator's
responsibility, and the documents make no claim about it.

## 22. Implementation phases

- **Phase 1 — Desktop shell + persistence + provider abstraction.**
  Tauri shell, screens skeleton, SQLite + migrations, `SecretStore`,
  `ProviderAdapter` trait + capabilities, settings, tray behavior.
- **Phase 2 — Codex account management + quota + CLI switching.**
  `CodexAdapter`, account CRUD, subscription/quota mapping, refresher,
  switching transaction with backup/verify/rollback.
- **Phase 3 — Antigravity account management + switching.**
  `AntigravityAdapter` behind the same contract; dual-provider GUI.
- **Phase 4 — Local gateway + account pools.** Loopback server,
  `/v1/models` + `/v1/responses` + `/v1/chat/completions`, pool
  membership, deterministic routing, safe retry/failover/cooldown,
  streaming, `RequestUsage` accounting.
- **Phase 5 — API Access Manager + usage/limits.** Clients/keys/policies,
  rotation UX, budgets/rate/concurrency enforcement, usage screens,
  retention pruning.

Order rationale: each phase is independently shippable and testable
against real clients before the gateway exists; the gateway (highest
risk) lands on proven account/switching foundations; access management
lands last because its enforcement needs real gateway traffic to verify.

## 23. Runtime update: Go web service foundation (implemented)

Supersedes the Tauri selection (§5–§7) for the working foundation. The
provider abstraction (§8), data models (§9, §14–§15), credential rules
(§10), switching transaction (§11), and routing/policy invariants
(§12–§13, §16) stand unchanged as future direction.

### 23.1 Current runtime

- Single Go executable (`cmd/ai-lb`), no Node.js runtime on user machines;
  React + TypeScript + Vite build embedded via `go:embed`.
- Control server (`127.0.0.1:8317` default): serves the web UI and the
  management API (`GET /api/health`, `GET /api/app`, `GET /api/settings`,
  `PUT /api/settings`, plus a same-origin `GET /api/gateway` liveness
  proxy so the browser needs no CORS).
- Gateway server (`127.0.0.1:8318` default): `GET /health` only; no
  OpenAI routes yet, unknown paths return controlled `not_found`.
- SQLite (`settings`, `app_metadata` tables only): auto-created in the
  OS-appropriate app data directory, migrated, foreign keys on, validated
  at startup. Ports configurable and persisted (`1..65535`, defaults
  unprivileged); listener ports apply on restart; busy ports fail fast
  with a clear error. Graceful shutdown on SIGINT/SIGTERM.
- Loopback-only for both listeners. No `0.0.0.0`, LAN, remote, or tunnel
  modes — not even as flags.
- `internal/providers`, `internal/routing`, `internal/secrets` exist as
  documented package skeletons only. No provider, OAuth, quota, routing,
  switching, proxy, key, or policy logic is implemented.

### 23.2 Future common router (documented, not built)

Control plane and data plane stay split: the control server owns settings
and (later) account/pool/policy state; the gateway resolves requests
through a common router over Codex and Antigravity pools. One ai-lb API
key may use both provider pools where request/model capabilities allow —
capability mismatch fails closed with a structured error, never with a
blind upstream attempt.

### 23.3 Future routing requirements (documented, not built)

- Automatic account failover on exhausted quota.
- Optional cross-provider routing.
- Session/conversation affinity on stable identifiers only; no prompt
  history stored for affinity (§13.1 rules apply).
- Capability-based routing (model features vs pool capabilities).
- Image input support where the upstream model supports it.
- System/developer instructions where supported.
- Future video capability tracked with no v0.1 video promise.

### 23.4 Future User Portal (concept, not built)

- **Admin UI** — the current web UI's growth path: accounts, routing,
  quotas, API clients, policies, settings.
- **User Portal** — a future, narrower surface per API consumer: own
  usage, remaining limits, allowed models, API endpoint, key status.
